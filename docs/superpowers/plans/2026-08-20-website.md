# lanthorn.dev — a plan for the project site

**Status:** plan only. Nothing built. Filed 2026-08-20.

## The one rule

**The site SHOWS. `docs/` EXPLAINS.**

If a sentence explains rather than captions, it belongs in the repository, not on
the page. The README and `docs/features/*` are already written, already accurate,
and already kept current by a standing rule — duplicating them onto a web page
creates a second copy of the truth that goes stale, which is the exact failure this
project spends most of its effort avoiding elsewhere.

So the site is not a rendered README. It is a gallery with captions and a download
button, and it links out to the repository for anything a reader wants to *read*.

## Shape

**Several small pages, each led by one image or recording.** Not one long scroll —
a detail-dense single page is the thing to avoid, and it is what a rendered README
would produce.

Target: a visitor understands what lanthorn is within one screen and one moving
image, and can download it without scrolling.

    /                 hero image, one sentence, download button, 4 tiles
    /map              the automapper
    /graphics         v6 artwork in a terminal
    /machines         fidelity — the showpiece
    /media            playing from original disks
    /download         per-platform assets from the latest release

Prose budget: a headline and one or two sentences per page. Captions may be longer
than body text; that is the correct ratio here.

## What carries each page

| page | asset | produced by |
|---|---|---|
| `/` | one real screenshot | a real Ghostty session — nothing synthesised beats it |
| `/map` | asciinema cast, TUI | recorded live; all cells, so the player captures it exactly |
| `/graphics` | short WebM + stills | screen recording; asciinema CANNOT show kitty graphics |
| `/machines` | cast + comparison grid | `zvm-cli --machines`, `--period-look`; `machine-screenshots/` |
| `/media` | stills grid | the SQ-0942 gallery tool |

## `/machines` is the showpiece

It is the claim nobody else on this shelf can make, and the one with the most
evidence already committed. It should be almost wordless: a grid of the same scene
across machines, and beside each, the real hardware capture from
`machine-screenshots/` that it was measured against.

Two casts belong here and both are pure text, so asciinema captures them whole:

  - `zvm-cli --machines` — the machine table printed in the ACTUAL colours: every
    machine modelled, its palette, period look, status band and cursor shape, with
    the provenance line "OBSERVED from emulator captures in machine-screenshots/".
    It makes the entire fidelity argument in about four seconds.
  - `zvm-cli --period-look "Zork I …adf"` — a Version 3 game off an Amiga floppy on
    the Amiga's own blue page with its block cursor, in a bare terminal. No TUI
    chrome between the viewer and the claim, which is why this leads rather than a
    TUI screenshot.

**Label which image is which kind of evidence.** A generated render beside a
hardware capture only works while a reader can tell them apart. See the caveat
below.

## The CLI clients earn their own space

`zvm-cli`, `gvm-cli` and `scott-cli` are text-only by design, so a cast captures
them COMPLETELY — no video needed, small files, selectable text. They also answer
an objection the TUI cannot: *"I want to play over ssh, in a pipe, in tmux, without
a full-screen app."*

Worth recording besides the two above:

  - `--pin bottom` — a frozen status line with real scrollback. Terminal-native
    behaviour that only exists in a recording of an actual terminal.
  - one cast per engine — three binaries, three games. Scott Adams is charmingly
    minimal and makes the range concrete faster than a sentence does.

## Hosting

**GitHub Pages.** Not for cost — every candidate is free — but because the release
binaries are already on GitHub and `docs/` is already markdown in the repo, so a
download link can point at the latest tag rather than being hand-updated, and the
site never has to restate what the docs say.

Cloudflare Pages is the equivalent-quality alternative and worth it if the image
count grows. Google Sites will work and supports a custom domain, but it puts the
content outside version control and handles monospace and code poorly — the wrong
trade for a developer tool.

Given six small pages and a desire for visual control, hand-written HTML and CSS is
probably better than a static-site generator: no build step, no theme to fight, and
the markdown stays where it already lives instead of being rendered twice.

## Two things not to do

**Do not claim typography from generated renders.** `pty_capture`'s output is
honest about layout, art placement and colour, and about nothing else — it draws
text with the repo's own bitmap face (Uni-VGA 8x16 since SQ-0932), which is not the
font in anyone's terminal. Since SQ-0932 made those pictures markedly better, the
temptation to read them as screenshots went UP; `tests/pty_stream/raster.rs` says
so at its head. Hero and marketing shots should be real screenshots.

**Do not let the site restate the docs.** Every feature page should end in a link
into `docs/features/`, not a summary of it.
